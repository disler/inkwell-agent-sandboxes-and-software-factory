Plan: Sandbox Mount System

feature · complex · measured on live VMs 2026-08-04

Where this stands 2026-08-04

Built and working: all six phases exist; five ran on live hardware. A real SDLC completed inside a sandbox (5/5 phases, 902k tokens, $0.528, commit bcfc678). Command surface is namespaced into sbx / adw / local / obs. The orchestrator skill and five prompts are authored.

Not yet proven, and the claim matters: the verified end-to-end run happened on a VM where the strip had been accidentally undone by a git checkout -- .. The strip has since been fixed (mod?, and mount relocated into the stripped directory) and confirmed in isolation, but a clean full mount with the strip genuinely in place has not been run. TEARDOWN has never been executed at all.

Outstanding

  • Clean e2e re-run with the strip in place — the headline claim depends on it.
  • Teardown unexercised. It is also the only thing that rescues a sandbox's commits (via git bundle) and records spend.
  • Vocabulary collision: a sandbox hosts many ADW runs, but the sandbox record calls itself run_id and duplicates it as vm_name. Rename to a single sandbox field is agreed in principle, not done.
  • just sbx execute cannot vary the roster — hardcoded to the module default, and ssh vm "cmd" carries no environment. Best-of-N cannot actually vary models until this is fixed.
  • Gate C reads SSSF_CONFIG inside the sandbox, where nothing sets it, so it always pings the default roster.
  • Naming asymmetry: just local cc vs just sbx orchestrate — same action, two conventions.
  • exedev vm snapshot still lacks sync before cp; the golden-VM path is unexercised.
  • Skill cookbooks still document the pre-namespace flat commands.

Task Description

Build the rebootable mount system that stands up Inkwell plus the Super Simple Software Factory on a throwaway exe.dev VM, runs work inside it, and lets us watch from outside without reaching in.

The system is split into two layers that must never mix:

Out-sandbox · orchestration host only

just/sandbox/*.just — six phase recipes that run on your machine and drive the exe.dev control plane. Stripped out of the mounted copy so a sandbox can never mount sandboxes.

In-sandbox · execution inside the VM

just/adws.just mounted as mod adw — the ADW workflows. This is what execute kicks off. It survives the strip and ships with the repo.

Objective

  • just mount RUN_ID takes a blank VM to a health-checked, running factory in ~10s, and stops at observe. It never tears down.
  • just adw <name> "..." runs any ADW inside the sandbox.
  • Three ways to drive a mounted sandbox: a generic command, the default full SDLC, and a persistent resumable agent session we can keep talking to.
  • just teardown RUN_ID is always an explicit, separate decision.
  • Getting one sandbox right makes N free: N is a loop over the same six phases.

Problem Statement

The factory has no home. It runs on the same laptop we work on, which caps us at one agent: five agents fight over one working directory, one dev server port, and one git state. Isolation is the mechanical blocker. Being forced out of the loop is the strategic one — a system that needs a human at every step does not scale, and that human becomes the key-man risk.

Everything below is grounded in measurements taken on real VMs, not inference. Several "obvious" designs were killed by those measurements:

AssumptionMeasured reality
Dependency install is slow, so bake a Docker image False. bun 1s, just 0s, bun install 0.4s, cold uv resolve 3s. A custom image buys ~1s.
Use --setup-script to self-configure Wrong tool. 10KiB cap, async, and it cannot see --env, so it can never receive the runtime key.
Pass secrets with --env Invisible. Lands in /etc/profile.d/exe-env.sh; not present for ssh vm "cmd".
Golden VM via cp is a free speedup Silently corrupts. Unsynced clone produced 5,641 zero-byte files and reported success.
Need the GitHub integration to clone Not for a public repo. Plain git clone, zero auth.

Solution Approach

One repo, two layers, one boundary. The boundary is the strip manifest: at setup time the sandbox deletes the orchestration layer from its own copy. The rule for which layer a file belongs to is simply what credential does it need?

Out-sandbox (orchestration)In-sandbox (execution)
Lives injust/sandbox/*.just, sandbox_mount/host/setup_sandbox.pyjust/adws.just, adws/, sandbox_mount/guest/provision.sh

Credentialexe.dev account + OpenRouter provisioning keydisposable runtime key only

Files come in via git clone against the public repo. That single choice removes rsync, the exclude list, .git special-casing, and the GitHub integration, while adding a commit-SHA pin that makes N runs comparable.

Build Phase 2 — The six runtime phases

1. CREATE host · control plane · 1.9s

Strict order. Every failure path calls just teardown <run-id>.

Gate: SSH responds. Must not: put code or secrets on the box — the key is minted here but injected in FILL.
# adjustable per run: just create my-run --limit 200
curl -s https://openrouter.ai/api/v1/keys \
  -H "Authorization: Bearer $OPENROUTER_PROVISIONING_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"name\": \"sbx-$RUN_ID\", \"limit\": ${LIMIT:-50.00}}"
# -> { "key": "sk-or-v1-...", "hash": "..." }
Why record → VM → key: a crash between any two steps must leave something teardown can find. Record first means teardown always has a handle. VM before key means a mint failure orphans a VM (cheap, visible in vm list) rather than a key orphaning spend (invisible). Teardown must be idempotent.
The sbx- prefix is load-bearing — it is how reap tells our keys from your personal ones. Verified: your four personal keys carry no such prefix. Never mint a managed key without it.

2. FILL host-triggered · runs inside · 2.6s

Gate: checked-out SHA equals the intended SHA.
Public repo, no auth, no GitHub integration. Measured at 2.61s for 216 files. The clone brings .git with it, which SSSF needs because its workflows commit their own output.
.env is written here, not at create — it lives inside the repo dir, which does not exist until the clone lands. --env cannot carry it.

3. SETUP inside · ~5s

ssh <vm> 'bash app/sandbox_mount/guest/provision.sh', which does in order:

The trace db must exist before OBSERVE. Verified: the visualizer refuses to start without it ([sssf] sssf.db not found, then exits). Since just mount ends at observe — before any ADW has run — a fresh sandbox would start a UI that dies instantly. The tracer's DDL is all CREATE TABLE IF NOT EXISTS, so initializing here is idempotent.

Gate — four assertions:

On fail: report and STOP. Do not destroy the VM. Leave it up so it can be debugged, exit non-zero, and keep just teardown an explicit decision. A gate that auto-destroys throws away the evidence you need to fix it.
The cost block is mandatory and all-or-nothing. pi defaults cost to all zeros when rates are absent, and agent_pi.py:276 reads usage.cost.total straight from pi — so a missing rate table means every run reports $0.0000 while really spending money. Observed: a 463.6k-token run logged $0.0000.

Worse, the schema requires all four fields (input, output, cacheRead, cacheWrite). A partial block fails validation and pi drops the entire roster, not just that model: must have required properties cacheRead, cacheWrite → No models available. Use 0.0 where a provider publishes no cache-write rate.

Verified fixed: with rates loaded, a 1,797-token run reported $0.0081.

4. EXECUTE host-triggered · returns instantly

Gate: returns immediately with a PID.
All three detachment pieces are required or SSH never returns: nohup, output redirect, < /dev/null. And --shell bash --shell-arg -c is mandatory — the justfile sets shell := ["zsh", "-ic"] and zsh is not in the image; installing it costs 35s of apt for no benefit.

5. OBSERVE host / browser

Gate: app returns 200 anonymously; visualizer returns 200 for the logged-in owner.
Verified end to end. Both served simultaneously from one sandbox, app anonymous, visualizer showing a real ADW trace and gated to the owner. Servers must bind 0.0.0.0; Bun does by default (ss -ltn shows *:4501).

6. TEARDOWN host · only when we decide

Gate: the key is absent from GET /api/v1/keys.
Do not verify revocation with GET /api/v1/key. Measured: immediately after a successful DELETE, that endpoint still returned 200 for the dead key while the authoritative key list already showed it gone. Assert on the list.

The provisioning key cannot do inference — it returns User not found. It mints and revokes only, which is why the gate ping must use the minted runtime key.
Artifacts are not enough. SSSF commits plan, code and docs separately; copying files down loses that history. 
ssh <vm> 'cd app && git bundle create /tmp/run.bundle main'
scp <vm>.exe.xyz:/tmp/run.bundle .sandbox/runs/<run-id>.bundle
git fetch .sandbox/runs/<run-id>.bundle main:sandbox/<run-id>
Order matters: artifacts out → revoke → destroy. A crash between revoke and destroy leaves a dead key rather than a live one.

Freeform

The two just gotchas that would have broken this design

Both verified locally on just 1.49 (VM runs 1.58) before writing this plan. mod is not import:

Behaviorimportmod chosen
Recipe namesflattened into rootnamespaced: just adw plan
Parent variablesinheritedNOT inherited — config is undefined
Working directoryrepo rootjust/ — adws/ is invisible
Parent settingsinheritedNOT inherited — positional-arguments silently lost
Fix requirednonefour lines at the top of the module
Found during the build, worse than the variable problem. Settings are not inherited either. Without set positional-arguments in the module, a recipe runs under sh with $@ empty — so just adw ask scout "where is auth" would have silently dropped every argument and run the agent with no prompt. No error, just a wrong run. The module also needs set dotenv-load, and a default recipe, because a bare just adw otherwise executes whichever recipe happens to be first in the file.

Also: just adw --list is not valid syntax in just 1.49 — it reads adw --list as a recipe name. The working form is just --list adw.
# just/adws.just — the two lines that make mod work
set working-directory := '..'                                    # else cwd is just/
config := env_var_or_default("SSSF_CONFIG", "adws/adw_sssf_config/sssf.config.yaml")

# read-only recon
scout *ARGS:
    uv run adws/adw_scout.py --config {{config}} "$@"
Without set working-directory := '..' every recipe fails with No such file or directory: adws/adw_scout.py. Observed, not theorized.

The three execute modes

# just/sandbox/execute.just

# generic: run any command inside a sandbox
run RUN_ID +CMD:
    ssh $(just _vm {{RUN_ID}}).exe.xyz 'cd app && {{CMD}}'

# default: full SDLC, detached, we step away
execute RUN_ID PROMPT:
    ssh $(just _vm {{RUN_ID}}).exe.xyz \
      'cd app && ( nohup just --shell bash --shell-arg -c adw sdlc "{{PROMPT}}" \
        > run.log 2>&1 < /dev/null & echo $! )'

# hand off to an agent we can keep chatting with
agent RUN_ID PROMPT:
    #!/usr/bin/env bash
    VM=$(just _vm {{RUN_ID}}); SID=$(just _session {{RUN_ID}})
    if just _agent_started {{RUN_ID}}; then FLAG="--resume $SID"; else FLAG="--session-id $SID"; fi
    ssh $VM.exe.xyz "cd app && ANTHROPIC_API_KEY=implicit \
      ANTHROPIC_BASE_URL=https://llm.int.exe.xyz \
      claude -p $FLAG --dangerously-skip-permissions '{{PROMPT}}'"
Verified working. Two separate SSH invocations, --session-id then --resume: turn 1 stored 42, turn 2 recalled 42. The session survives the SSH connection dying, which is what makes "hand off but keep talking" real rather than aspirational.

Zero data retention

All nine verified ZDR-capable on 2026-08-04 — every model returned pong under provider: {"zdr": true, "data_collection": "deny"}.

provider.zdr true / omitted
Route only to providers enforcing zero data retention.
provider.data_collection allow (default) / deny
deny restricts routing to providers that do not collect user data. Independent of zdr; use both.
Enforcement is an account setting, not per-request. pi's models.json supports custom headers but no arbitrary request-body fields, so provider: {...} cannot be injected through pi's config. Set the data policy once in the OpenRouter dashboard (Settings → Privacy); it then applies to every request from every key including minted runtime keys, and covers Claude Code too. The per-request param stays in the gate ping so the gate proves ZDR routing resolves before any real work runs.
This sharpens the IP-hygiene beat. Under ZDR, deepseek-v4-flash-0731 is served by Parasail and glm-5.2 by CoreWeave — both US providers. The "Chinese labs may train on your data" caution applies to those labs' own APIs, not to their open weights on Western hosts. Under ZDR you are not talking to a Chinese lab at all.
Two id corrections from verification. There is no deepseek v3 0731 — the v3 line ends at v3.2; the 0731 build is deepseek-v4-flash-0731. And moonshotai/kimi-k3 is $3.00/$15.00, about 5x kimi-k2.6 ($0.59/$2.48) — good as a frontier lane, expensive as a default builder.

Credential lifecycle

Provisioning key host only, long-lived
Lives in OPENROUTER_PROVISIONING_KEY on your machine. Never enters a sandbox, never committed, never mounted. The only long-lived secret in the system.
Runtime key per sandbox, $50 default
Minted in CREATE as sbx-<run-id>, injected in FILL via .env, spend captured and key revoked in TEARDOWN by hash. --limit is per-run adjustable; $50 is the default because a real SDLC run will blow through a token cap and die mid-workflow, which looks like a bug rather than a budget.
Reaper backstop
OpenRouter keys have no native TTL. If teardown never runs, the key outlives the sandbox. just reap deletes every sbx- key whose VM is gone or whose record is closed. Run it at the start of every session. The prefix is the only thing separating managed keys from your personal ones.

Why OpenRouter and not exe.dev's BYOK integration

exe.dev integrations can hold your OpenAI, Anthropic, Fireworks and xAI keys and serve them at llm.int.exe.xyz with no key on the VM at all — verified working. It was seriously considered and rejected:

CriterionOpenRouter chosenexe.dev BYOK

Portability is the disqualifier. A credential layer built on a provider-specific hostname stops being a transferable asset the moment the sandbox provider changes, and the whole point of this system is that it moves.

The managed gateway stays untouched. llm.int.exe.xyz is already attached auto:all and serves 74 models with zero keys configured. We build nothing on it, but it gives this public repo a real property: anyone who clones it onto an exe.dev VM gets working agents without configuring a single credential. Verified with both claude and pi.

Observability: two ports, one login

Hosting two servers is unlimited. Only one port can be anonymous, and it is whichever share port names — "public" is a property of that port, not of the VM. Give it to the app; the agent view is then private by default, and transparent to you because your browser already holds an exe.dev session.

SurfacePortAnonymousYou (logged in)Command
Inkwell app4501200200share port <vm> 4501 + share set-public
SSSF visualizer4600307 → login200nothing — alternate ports 3000-9999 are forwarded automatically
Verified end to end. Both surfaces served simultaneously from one sandbox: the app anonymously public, the visualizer showing a real ADW trace and gated to the owner. No extra machinery, no reverse proxy, no tunnel.

The VM-scoped bearer token is for automation only — headless Chromium has no exe.dev cookie, so the Playwright validation gate needs X-Exedev-Authorization: Bearer <token>. The token cannot be embedded in a URL for browser use: Chromium strips credentials before sending, so https://x:TOKEN@vm.exe.xyz:4600/ lands on the login page even though curl -u with the same token returns 200.

Servers must bind 0.0.0.0. Bound to 127.0.0.1 the proxy cannot reach them and the URL silently 502s. Default proxy port is 8000 (from EXPOSE in exeuntu), which is not Inkwell's 4501 — the remap is mandatory, not cosmetic.

Why N is nearly free

Best-of-N means N separate sandboxes, not N agents inside one. Each is a full six-phase run with its own VM, own key, own ports, own record. The loop is the only new code, and per-run variance lives in exactly three places: the prompt, SSSF_CONFIG, and the model.

Golden-VM path (worth it around N ≥ 3)

sync then cp replaces CREATE and most of SETUP: 0.37s instead of ~10s, arriving with warm node_modules, warm uv cache and models.json in place. FILL always runs, because a clone's code is stale by definition.

The sync is not optional. Skipping it produced 5,641 zero-byte files with no error of any kind. This is why gate #1 hashes content rather than checking that files exist.

Rejected: one sandbox running N agents

Defeats the purpose. The whole reason for the sandbox is that N agents cannot share one filesystem, one port range, and one git state. Putting them back together reintroduces exactly the collision the system exists to remove.

Rejected: --setup-script as the provisioning mechanism

Three disqualifiers, all measured: 10KiB cap; runs async via exe-setup.service so new returning means nothing; and it cannot see --env, so it can never receive the minted runtime key. Push code, then run provision.sh over SSH — synchronous, uncapped, debuggable, versioned with the repo.

Notes

  • No new dependencies. Everything uses just, ssh, curl, and the vendored exedev CLI already in the repo.
  • Every number in this plan is measured. The last estimate, phase 2, was closed at 2.61s by a full end-to-end run: clone → provision → real ADW → both surfaces served and validated in a browser.
  • Public repo. github.com/disler/inkwell-agent-sandboxes-and-software-factory. Clone needs no auth. Pushing a results branch would need the GitHub integration; V1 pulls artifacts down over SSH instead, keeping zero credentials in the sandbox.
  • Deferred: /sssf-sandbox-orchestrator, a composite skill combining /sssf and /sandbox-exe-dev awareness, is what will drive 1→N. It is out of scope here and becomes tractable once one sandbox is solid.
  • Known cosmetic issue: exe.dev ships a pi extension that errors on every invocation (unrecognized reflection shape). Harmless, but it writes to stderr, which matters if the factory parses agent output.
  • Migration: just sdlc → just adw sdlc is a breaking change to a public repo's documented interface. SSSF cookbooks reference the old form.
